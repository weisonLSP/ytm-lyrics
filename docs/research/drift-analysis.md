# drift 校正过频诊断报告（TASK-403 Part B）

- 日期：2026-08-12
- 范围：只诊断 + 单测，不改生产逻辑（阈值改动需真机校准，沙箱数据不足以支撑）
- 结论先行：**「drift 校正过频」不是阈值 bug，是观测噪声 + 真实事件驱动的正常校正**。0.8s 阈值对 ±50ms 传输抖动有 8 倍余量，对实际 loopback 抖动（<5ms）有 80 倍余量；稳态播放下校正触发频率 = 0。

## 1. 背景

HANDOFF backlog 记录「drift 校正过频」未修。TASK-205H 在 `PlaybackStateMachine.OnSnapshotReceived` 加入了 drift 观测日志：

```
[PlaybackStateMachine] drift X.XXs > 0.8s, accept snapshot (seek correction) [transport=XXms, seq=XX]
```

「过频」的原始观感来自这类日志行频繁出现。本报告用注入时钟 + FakePlaybackProvider 模拟快照序列，判定该行为是阈值敏感 bug 还是正常机制在特定输入下的表现。

## 2. 机制推导

状态机位置外推（ADR-6）：

```
display = base.Position + (now − base.ArrivedAt)        // Playing 时
```

新快照到达时，若 |外推值 − 快照值| > 0.8s 则接受快照并重置基准（seek 校正），否则保持旧基准。

设快照 k 为当前基准，快照 i 为到达帧。偏差推导：

```
偏差 = |base.Position + (ArrivedAt_i − ArrivedAt_k) − Position_i|
     = |(SentAt_i + Δ_i) − (SentAt_k + Δ_k) − (SentAt_i − SentAt_k)|      // 1x 播放：Position_i = Position_k + (SentAt_i − SentAt_k)
     = |Δ_i − Δ_k|
```

其中 Δ = ArrivedAt − SentAt 为传输延迟。**探针/桌面端时钟差是常数，两帧相减时抵消**（即使 transport 显示为负值，也不影响校正判定）。

结论：稳态播放下校正偏差 = **相邻帧传输延迟之差**，与播放时长、心跳间隔无关。±50ms 抖动 → 偏差 ≤ 100ms << 0.8s 阈值。

## 3. 模拟方法

- 载体：`PlaybackStateMachineTests.drift诊断_*` 系列（新增 4 个测试，固定种子/确定性序列，可复现）
- 注入：FakePlaybackProvider 手动 Push `PlaybackSnapshot`，时钟注入 `() => now`，now 与帧到达时刻对齐
- 输入模型：1x 稳态播放，2s 心跳（与探针 `HEARTBEAT_MS=2000` 一致），position 精确 = 播放位置

## 4. 模拟结果

### 4.1 稳态 ±50ms 随机抖动（60 帧 = 120s）

- 传输延迟 U(−50, +50)ms，固定种子 403
- 校正触发次数：**0**
- 相邻帧显示步进偏移（相对 2s 心跳）：≤ 0.15s（上界实测远小于此，见下）
- 最终位置与真实播放位置偏差：≤ 0.15s

### 4.2 时钟差常数 + 抖动（30 帧 = 60s）

- 探针时钟快于桌面 700ms（transport 恒为负值，模拟真实时钟不同步），叠加 ±50ms 抖动
- 校正触发次数：**0**（时钟差常数被两帧相减抵消，与推导一致）

### 4.3 确定性最坏情况扫描（定位触发边界）

交替注入 +m/−m 传输延迟，使相邻帧延迟差恒 = 2m（最坏情况），200 帧：

| 抖动幅度 m | 实测最大偏差 | 是否触发 |
|---|---|---|
| 100ms | 0.200s | 否 |
| 300ms | 0.600s | 否 |
| 399ms | 0.798s | 否 |
| 400ms | 0.800s | 是（浮点 0.80000000000000004） |
| 401ms | 0.802s | 是 |
| 500ms | 1.000s | 是 |

实测偏差**精确等于 2×m**，实证「偏差 = 相邻帧传输延迟差」。触发临界在 ±400ms。

### 4.4 真 seek 在抖动场景下仍能校正（guard）

稳态抖动 20s 后注入 +5s 真实 seek：校正正常触发，位置跳到 35s 并继续外推。0.8s 机制不误杀真跳变。

## 5. 结论

### 5.1 「过频」不是阈值 bug

| 证据 | 数值 |
|---|---|
| ±50ms 抖动（任务卡假设的最坏传输场景） | 0 次误触发，8 倍阈值余量 |
| 实际 loopback 传输抖动（本地 WS，<5ms 量级） | ~80 倍阈值余量 |
| 触发临界抖动幅度 | ±400ms（相邻帧延迟差才可能越阈） |
| 位置连续性 | 稳态下步进偏移 ≤ 0.1s，无感 |

0.8s 阈值是 PRD §5 F2 的既定规格（|漂移| > 0.8s 触发歌词跳行），模拟证实其在正常网络条件下有充分余量。**阈值不敏感。**

### 5.2 「过频」的真实来源：观测噪声 + 真实事件

drift 日志行只会在 |偏差| > 0.8s 时打印，而该偏差只可能来自**真实的位置跳变**，不是稳态噪声。可能造成日志行密集的场景：

1. **用户拖动进度条（seek）**：YTM 拖动即发 `seeked` → 探针事件帧 → 一次校正。连续拖动 = 连续日志行。这是**正常且必要**的校正（位置确实跳了）。
2. **切歌/暂停/恢复**：播放状态切换重置基准（不打印 drift 行），但切歌瞬间 position 归零也会触发一次校正。正常。
3. **多 YTM 标签页同时开探针**（多实例竞争，TASK-205H 注释已提及）：多个连接各自发布快照到同一状态机，不同曲目/不同进度交替到达 → 每次来源切换都是大偏差 → 密集校正。这是**最可能被误读为「过频」的结构性场景**，但它本质是输入源竞争，不是阈值问题。
4. **浏览器后台 tab 节流**：心跳变稀疏后位置仍精确（audio.currentTime 不受节流影响），偏差仍 = 相邻帧延迟差，不放大过频。

### 5.3 裁决与建议

- **不改阈值**（0.8s 合理，模拟证实余量充足）；**不采用**滞回（持续 N 帧超阈才校正）或自适应阈值——它们解决的是一个不存在的问题，且会延迟真实 seek 的响应（位置跳变后歌词要慢半拍才跟随）。
- 若真机（用户侧）确认日志确实刷屏：**优先排查多标签页场景**（关闭多余 YTM 标签；或未来在探针侧加 instance id 由桌面端选主，属协议扩展，v1 不做）。
- 若希望减少日志噪音，可把 drift 行从 Trace 降级/合并（纯观测改动，与校正行为无关），不做也成立。
