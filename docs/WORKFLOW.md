# 协作流水线章程（WORKFLOW）

本项目采用三角色流水线。本文件是各环节的契约，任何执行 agent 介入前必须先读本文件与 PRD。

## 1. 角色

| 角色 | 模型（历史绑定记录） | 职责 | 成本定位 |
|---|---|---|---|
| 架构师 | kimi-k3（奥林/raphael） | 设计决策、任务卡签发、压缩摘要评审、偏差裁决 | 贵，只花在刀刃上 |
| 执行者 | deepseek-v4-flash（kathrik） | 调研、编码、测试、写文档草稿、读原始材料 | 便宜，承担所有重活 |
| 压缩器 | deepseek-v4-flash（独立只读实例） | 把执行产出压缩为结构化摘要，对照任务卡核查完整性 | 便宜，架构师的眼睛 |

> 角色与模型的绑定由戈塔什大人按当期工具指定，上表模型列是历史记录而非硬约束。当前架构师由用户在会话中指定；执行者经本机 HanaAgent 调度。

**核心原则：架构师不读原始产出全文，只读压缩器出品的摘要。** 例外：接口签名、协议帧、关键算法 diff，架构师可直接抽查。

## 2. 流水线运转

```
架构师签发任务卡（TASK.md 或会话指令）
  → 执行者执行（可读全文材料、写代码、跑测试）
  → 压缩器（独立实例）读取产出目录 + 任务卡，产出压缩摘要
  → 架构师读摘要，做三种裁决之一：通过 / 返工（指明偏差）/ 升级讨论（涉及决策变更）
```

为什么压缩器是独立实例：执行者压缩自己的产出会护短，倾向隐瞒返工成本与未遂方案。独立只读实例没有这段上下文，压缩更客观。日常小任务可降级为执行者按模板自压缩，里程碑节点必须使用独立压缩器。

**subagent 实例会被系统回收（活不过约 1~2 小时），所有认知必须随时落盘，commit 即保险。**

## 3. 任务卡格式（架构师签发）

```markdown
# TASK-<编号>：<标题>
- 目标：一句话，可验收
- 输入：相关文档/代码路径，必读清单
- 产出：文件路径清单 + 验收标准（对应 PRD 条款号）
- 边界：明确禁止做的事（如"不许动 Core 层接口"）
- 上报：完成后将产出目录交给压缩器，禁止直接向架构师汇报全文
```

## 4. 压缩摘要模板（压缩器产出，≤ 600 字）

```markdown
# 摘要 TASK-<编号>
- 结论：通过 / 部分通过 / 受阻（一句话）
- 产出清单：文件路径 + 每个文件一句话说明
- 偏差：与任务卡不符之处，逐条列出（没有则写"无"）
- 决策点：执行中遇到的、任务卡未覆盖的选择，及执行者的临时选择
- 待裁决：需要架构师回答的问题，编号列出
- 验收自评：对照验收标准逐条打勾/叉
- 建议抽查：1~3 个最值得架构师亲自看的代码位置（文件:行号 + 理由）
```

## 5. 评审标准（架构师读摘要时检查）

1. 产出是否覆盖任务卡全部验收标准
2. 偏差是否触及 PRD 已冻结决策（触及 → 必须升级，不许执行者自行变通）
3. 决策点的临时选择是否埋了架构债
4. 建议抽查点是否真值得看（抽查后更新对执行者的信任评级）

## 7. 调试预算与失败现场（成本控制硬条款）

调试是 token 经济里的黑洞。以下条款为强制执行项：

1. **三轮预算**：执行者对同一问题最多尝试 3 轮修复。第 3 轮仍未解决，必须立即停止一切尝试，产出失败现场快照，交给压缩器汇总后由架构师裁决：换方向 / 架构师亲自抽查 / 降级方案。**禁止发起第 4 次尝试。**
2. **失败现场快照模板**：
   - 症状：错误信息原文 + 复现步骤
   - 假设：当前认为的原因，按可能性排序
   - 已试：每轮试了什么、结果如何
   - 排除项：已确认无关的因素
   - 现场：相关文件:行号、日志关键行
   快照的意义：认知成本只付一次。换实例或换方向时，接手方读快照即可，不重烧上下文。
3. **交付前自测**：执行者交付必须附自测证据（测试通过记录 / 运行日志 / 截图），证明验收标准已亲自跑通。无自测证据的交付由压缩器直接打回，不消耗架构师评审。
4. **禁止事项**：为跑通而修改验收标准；注释掉失败的测试；未经任务卡授权修改 Core 层接口；为修 bug 顺手重构无关代码。

## 8. 权限与提权规则（戈塔什大人亲定，全员遵守）

1. 用户对某个目标行为的授权，不自动等同于对权限提升的授权。
2. 优先使用当前沙箱/当前权限执行任务。不要因为预判可能需要更高权限，就直接请求 elevated。
3. 如果命令失败：先读取并分析实际错误信息；判断失败原因是否确实与权限、沙箱或系统目录访问有关；不要仅凭“可能是权限问题”就提权。
4. 如果确认当前权限不足，并且提升权限是完成用户明确要求的任务所必需：向用户说明为什么需要提升权限；明确说明提升权限后将执行什么操作；在获得针对该权限提升的授权后，再使用 require_escalated。
5. “用户说帮我安装/帮我修复/帮我配置”只能视为对目标任务的授权，不能自动解释为对管理员权限、沙箱绕过、系统目录写入或任意命令执行的授权。
6. require_escalated 只能用于完成当前明确任务所必需的操作。不得因为调试方便、减少步骤或提高成功率而主动提权。
7. 提权后尽量只执行完成当前任务所需的最小命令，不要在 elevated 环境中执行无关的探索、清理或修改操作。
8. 如果提权失败：不要无限重复 require_escalated。分析失败原因后，向用户报告并寻找不需要提权的替代方案。
9. 不允许形成以下循环：command failed → assume sandbox → require_escalated → failed → require_escalated again。
10. 对具有破坏性、持久性或高权限影响的操作（删除系统文件、修改系统服务、修改安全策略、防火墙、凭据、启动项等），即使目标任务涉及这些操作，也必须先明确说明风险。

**执行细则**：本规则同时约束架构师与所有执行 agent。执行 agent 在任务中遇到权限受阻，按 §7 失败现场快照上报，禁止自行请求提权；提权决策权归架构师与戈塔什大人。

## 9. 交接文档卫生（2026-08-16 新增）

交接文档是耗材，不是档案。档案归 git 与 docs/history/。

1. **HANDOFF.md 只保留「当前真相 + 开口事项」**；增量日志在完成超过 7 天后移入 `docs/history/YYYY-MM.md`，HANDOFF 里只留一行指针。
2. **任务卡验收通过后移入 `docs/tasks/done/`**（用 git mv，保留历史）。
3. **研究草稿**被正式文档吸收后，在文首标注归档指向（如 ui-spec-draft.md → UI_SPEC.md），不再更新。
4. **冷启动预算**：新会话上手阅读（HANDOFF + BUGS + 当日任务卡）控制在 ~6KB；深文档（TDD/PRD/UI_SPEC/research）按需经 AGENTS.md 路由，禁止默认全读。
5. **卫生责任**：每次会话收尾时由当值架构师检查执行；瘦身动作本身记入 HANDOFF 顶部的「最后更新」行。
